
## 1. Как запустить

1. Клонировать репозиторий

```bash
  git clone https://github.com/maxbek97/TestCI.git
```
2. В папке с docker-compose.yaml создать файл .env с следующими параметрами

`POSTGRES_HOST`=postgres

`POSTGRES_DB`=Digi_Rub

`POSTGRES_USER`

`POSTGRES_PASSWORD`

`POSTGRES_PORT` - желательно какой-нибудь незанятый (допустим 5433)

`SECRETKEY` - задать для генерации JWT (допустим supersecretkey_32+luavreasswordskibidis)
Go to the project directory

3. В папке с docker-compose.yaml запустить команду

```bash
  docker-compose up --build
```
Дальнейшая установка, настройка связей между таблицами, и прочая организация создается автоматически с помощью миграций

## 2. Вопросы об архитектуре

#### 1. Модель данных

Была создана БД из следующих таблиц(описываю только те, которые касаются проектной области):

`"Название_таблицы"`:`{"поля таблицы"}` - `(ограничения)`

"Client": {"ФИО, mid - код системы банка, Id_Dr - код платформы ЦР"} mid - PK, ID_dr - nullable Unique

"DR_Wallet": {"Id_DRW - код платформы ЦР кошелька, client_Id, Id_bill - номер счета, status"} Id_drw - PK, client_id - FK по Client(mid), status - одно из фиксированных значений Prcs, Actv, Blck, Clsd

Между Клиентом и кошельками связь одна ко многим (1 клиент - много кошельков)

Остальные таблицы (users, refreshTokens) сделаны для авторизации, и таблица logs для логирования операций в системе

#### 2. Архитектура HTTP API
1. Был выбран исходя из ТЗ `Clean Architecture` подход, с элементами `DDD`, а именно. Вместо привычного конвейера Controllers <-> Service <-> Ef layer <-> DTO/MOdels была реализована следующая структура:

`Controllers` - так и остаются точками входа назначением которых принять и вернуть результат клиенту

`Application/` - В которых мы определяем use cases и разделяем их исходя из предметной области по папкам, а те в свою очередь по отдельным действиям, что мы выполняем над объектом

`Request/Result` - формы для принятия\отправки данных от верхнего слоя эндпоинта к нижним handlerам

`Handlers` - Слой, отвечающий за предобработку некорректных ответов

`Domain` - Объекты предметной областис описанными допустимыми\недопустимыми правилами использования. Именно в них описаны требования из ТЗ

`Irepository` - контракт, скрывающий реализациию работы с БД от Handlers

`Repository` - собственно реализация этого контракта. На этом слое происходит работа с БД


#### 3. Какие допущения были сделаны
В на уровне БД а главное на уровне Domain были обеспечены требования предметной области, а именно:

    1) переходы состояний кошелька
    2) Невозможность создания объектов с одинаковыми значениями полей (клиенты с одинаковыми Id_dr, mid; кошельки с одинаковыми Id_Dr, Id_bill и т.д)
    3) Невозможность изменения объектов с заполненными значениями полей (Нельзя переприсвоить значение Id_Bill у кошелька)
    4) невозможность создания кошелька с неактивным статусом

Из допущений следует отметить неоднозачность ТЗ в разделе с описанием статусов, а именно путаницу вносит Обозначение статусов `Prcs`, `Actv`, `Blck` активными, когда сущесвует сам статус `Actv` - Активный. В связи с этим требование

```
У клиента может быть несколько кошельков за всё время, но активный в каждый
момент только один
```
было реализовано так, что невозможно создать кошельки, пока есть хотя бы один кошелек со статусом не `Clsd`

Второе допущение было сделано исходя из такой формулировки ТЗ

```
Клиент может получить идентификатор участника на платформе ЦР. Этот идентификатор появляется не сразу и не обязан быть у каждого клиента...
```

Оно подсказало, что выдача кода платформы ЦР может быть как и извне, так и здесь на сайте. Именно второй подход я реализовал случайным присваиванием.

Ну и возможно очевединый вопрос будет, касательно 3го допущения:
```
А почему идентификаторы пользователей, кошельков в Guid а не в обчных Int?
```
Ну я подумал что такие ключи, они не могут являться простым числом, а являются буквально ключом. Как реквизиты какие-нибудь.

## 3. Что бы улучшили при большем времени

#### 1. Пагинация

Одну из идей для улучшения я смог реализовать, а именно пагинация о которой в ТЗ было не написано. Я подумал, что раз речь идет о клиентах банка (в отличии от кошельков клиентов), то значит их будет очень много, что прямо кричит о том, что это узкое место нужно оптимизировать и разгружать.

#### 2. Логирование
Ну это очевидно также. Для поддержания безопасности необходимо логировать операции производимые в системе. Для этого была создана таблица `Logs`, которая содержит время операции, над какой таблицей проводилась какая операция, и самое главное - кем проводилась.

#### 3. Авторизация
Также я смог реализовать эту идею, которая является подзадачей для логирования. Были созданы таблицы `user` и `refreshTokens`, которая содержит данные об операторах, которые должны работать с этой системой (email, password, login). Аутентификация сделана методом JWT Bearer

#### 4. Переезд на полноценный UI фреймворк
Vanila Js это конечно хорошо, но убрав React мы лишаемся адекватной поддержки состояний, перебрасывания аргументов между компонентами, более строго обеспечения контрактной совместимости на уровне типов, если мы говорим о React TS.
